## What the exam really tests

AI-300 is an **operations exam for two kinds of model**: classic machine learning in Azure Machine Learning (MLOps) and generative AI apps and agents in Microsoft Foundry (GenAIOps). Microsoft calls the combination AIOps. DP-100 asked you to *be* the data scientist. AI-300 asks you to build the factory the data scientist works in, and to run what comes out of it.

Themes and depth:

- **Workspace platform (MLOps infrastructure).** Workspaces, datastores, compute targets, identity, data assets, environments, components, and registries for sharing across workspaces. All of it is deployed as code with Bicep and Azure CLI, automated by GitHub Actions, with workspace network isolation and Git source control.
- **Model lifecycle, the largest domain.** MLflow tracking, AutoML, hyperparameter sweeps, training scripts and distributed training, pipelines, and comparing jobs. Then MLflow model registration with a packaged feature retrieval specification, responsible AI evaluation (the Responsible AI dashboard), archiving, managed online and batch endpoints, blue/green traffic splitting and rollback, drift monitoring and retraining triggers.
- **GenAIOps infrastructure.** Foundry resources and projects deployed with Bicep, managed identity with RBAC, private networking, serverless API compared with managed compute deployments, model versioning, provisioned throughput units, and prompts treated as versioned, comparable artefacts in Git.
- **Quality and observability.** Building evaluation datasets, quality metrics (groundedness, relevance, coherence, fluency), risk and safety evaluations, automated evaluation in pipelines, continuous monitoring in Foundry, latency, throughput, token cost and tracing.
- **Optimisation.** RAG tuning (thresholds, chunk sizes, hybrid search, embedding model choice, A/B tests) and fine-tuning: methods, synthetic data, monitoring, and promotion from development to production.

Where candidates lose points:

- They answer from the Azure ML SDK v1 or the old designer era. The outline assumes CLI v2 and SDK v2 YAML assets, MLflow-native tracking and managed endpoints.
- They mix up registries (share across workspaces) and workspace assets (local), or environments (runtime) and components (reusable pipeline steps).
- They mix up deployment billing models: serverless API (pay per token), managed compute (pay per VM hour) and provisioned throughput units (reserved capacity for predictable high volume).
- They treat prompts as code comments rather than versioned artefacts with variants and evaluations.
- They never ran a GitHub Actions workflow with OIDC federated credentials to Azure.

## Study strategy

1. **Foundations.** Revisit Azure identity (managed identity, service principals, federated credentials for GitHub), private endpoints and Bicep basics. AZ-900 gives you the vocabulary. AZ-204 prep gives you SDK authentication and Key Vault habits.
2. **Azure Machine Learning hands-on.** Create a workspace with Bicep, then work with data assets, environments and a compute cluster. Train with MLflow autologging, run a sweep and an AutoML job, build a two-step pipeline from components, register the model, deploy it to a managed online endpoint with two deployments, shift traffic, then roll back. Add a batch endpoint and a data drift monitor.
3. **GitHub Actions.** Put the whole thing in a repository. Lint, provision with Bicep, submit training and deploy on merge, using OIDC to authenticate to Azure.
4. **Foundry GenAIOps.** Deploy a Foundry project with Bicep and private networking. Deploy one model as serverless and one on managed compute, keep prompts in Git with variants, run evaluation flows with built-in and custom evaluators in CI, and turn on tracing and continuous monitoring.
5. **Optimise.** Tune a RAG pipeline: chunk size, top-k, similarity threshold, and hybrid compared with vector search. Then fine-tune a small model with synthetic data and compare it with the base model in an evaluation run.
6. **Official resources.** The certification page links the self-paced learning paths ("Prepare for the exam"). There is also the [study guide](https://learn.microsoft.com/en-us/credentials/certifications/resources/study-guides/ai-300), the [exam sandbox](https://aka.ms/examdemo) and the AI Skills Navigator practice assessment.

How your background helps or misleads:

- **CKAD prep** helps with deployment ideas (rolling and blue/green, health probes, scaling), and managed online endpoints follow the same mental model. It misleads if you reach for AKS everywhere: the outline prefers managed endpoints.
- **AZ-204 prep** helps with identity, Key Vault and CLI fluency.
- **.NET and Angular.** Little direct use. The exam is Python, YAML and Bicep. The "data science background" in the audience profile is the gap to close: know what a training script, a metric and overfitting are.
- **AI-103 knowledge** (if taken first) covers much of domains 4 and 5 from the builder's side, but AI-300 asks how to automate and govern those steps.

## Differences from related exams

- **AI-300 vs DP-100 (predecessor).** DP-100 was data science on Azure Machine Learning: exploring data, training, featurisation, plus some deployment and a late-added language-model optimisation area. AI-300 shifts from doing the science to operating it. It adds infrastructure as code, GitHub Actions, network isolation, registries, progressive rollout and drift-triggered retraining, and gives generative AI operations in Foundry 40–55% of the exam (domains 3 to 5).
- **AI-300 vs AI-103.** AI-103 builds AI apps and agents. AI-300 provides the infrastructure, pipelines, evaluation gates and monitoring for them, and adds the classic ML lifecycle that AI-103 does not cover.
- **AI-300 vs AI-500.** AI-500 is expert-level design and build for multi-agent systems. AI-300 is associate-level operations for models and generative AI apps. Both ask for CI/CD and tracing, but AI-500 applies them to agent teams.
- **AI-300 vs MLA-C02 (AWS Certified Machine Learning Engineer – Associate).** These are the closest match in role and level: an engineer who prepares data, trains, deploys and monitors models with CI/CD. The AWS exam centres on Amazon SageMaker AI (Data Wrangler, Feature Store, training jobs, Model Registry, endpoints, Pipelines, Model Monitor) and puts more weight on data preparation and feature engineering. AI-300 puts almost no weight on data preparation, but adds a generative AI half (Foundry deployments, prompt versioning, evaluations, fine-tuning, RAG optimisation). Mapping: MLflow and workspace registry to SageMaker Experiments and Model Registry, managed online endpoints to SageMaker real-time endpoints, Azure ML pipelines to SageMaker Pipelines, model monitoring to Model Monitor, Foundry to Amazon Bedrock. As of 2026-10-24 the [AWS certification page](https://aws.amazon.com/certification/certified-machine-learning-engineer-associate/) says MLA-C02 has been in beta since September 29, 2026, keeps the MLA-C01 domain structure, and replaced MLA-C01 in English after September 28, 2026. Check its exam guide for the exact task statements.
- **AI-300 vs AZ-400 or AZ-401 (DevOps).** The DevOps exams cover CI/CD, source control and release strategy for any workload. AI-300 applies a subset of that to models and prompts, with GitHub Actions as the named tool.

## Exam-day notes

- You have 120 minutes. YAML and CLI questions are quick if you have run the commands and slow if you haven't. Mark them and move on rather than guessing at syntax.
- Microsoft Learn is available. The Azure ML CLI v2 reference and YAML schema pages are worth knowing where to find, but searching costs time.
- Watch for v1 artefacts in the options (ScriptRunConfig, Estimator, old dataset classes, ACI web services). They are usually distractors.
- "Share models across teams or workspaces" points to registries. "Predictable high-volume generative traffic" points to provisioned throughput units. "Roll back safely" points to deployment traffic weights on one endpoint.
- Breaks lock you out of questions you have already seen. Finish your marked items first.
